# Отчёт по лабораторной работе 2

1. Цель работы

Цель работы — научиться управлять поведением большой языковой модели с помощью системных инструкций и параметров генерации, экспериментально исследовать влияние temperature и ограничения длины ответа, а также подобрать воспроизводимую конфигурацию для практической задачи первичного анализа события информационной безопасности.

В ходе лабораторной работы требовалось провести серию повторных вызовов одной модели, сохранить фактические параметры каждого запроса, измерить задержку, оценить следование инструкциям и на основании наблюдаемых результатов сформировать рекомендуемую конфигурацию.

3. Исследованные параметры и организация эксперимента

В рамках основной части были исследованы три группы настроек: системная инструкция, параметр temperature и ограничение длины ответа. Дополнительно была проверена итоговая конфигурация для прикладного сценария информационной безопасности.

System prompt: три варианта системной инструкции для одного и того же события ИБ.

Temperature: значения 0.0, 0.3, 0.7 и 1.0; для каждого значения выполнено по пять повторов.

Ограничение длины: max_tokens = 100, 300 и 800 для одного объёмного запроса об архитектуре RAG.

Практическая конфигурация: system prompt для аналитика ИБ, temperature = 0.2, max_tokens = 400, фиксированный формат ответа.

Всего программой выполнено 30 API-вызовов. Ошибок API не зафиксировано. Средняя задержка по всем вызовам составила 4.528 с. Для каждого результата сохранялись модель, вид эксперимента, system prompt, temperature, max_tokens, номер повтора, задержка, причина завершения, статистика токенов, ответ и текст ошибки.

Для исследования роли системной инструкции использовался один пользовательский запрос: «Событие: в 03:17 зафиксировано 25 неудачных попыток входа в учётную запись admin с одного IP, после чего произошёл успешный вход. Проанализируй ситуацию». Изменялся только system prompt.

8. Влияние ограничения длины ответа

Для исследования max_tokens использовался объёмный запрос об архитектуре RAG-системы с семью этапами: ingestion, chunking, embeddings, vector database, retrieval, prompt construction и generation. Для каждого этапа требовалось указать назначение и одну типичную ошибку.

| max_tokens | Время, с | Токены ответа | finish_reason | Достаточность | Наблюдение |
| --- | --- | --- | --- | --- | --- |
| 100 | 1.362 | 100 | length | Нет | Ответ обрывается во вводной части и не переходит к требуемым этапам. |
| 300 | 3.651 | 300 | length | Нет | Описан только первый этап; ответ обрывается из-за лимита. |
| 800 | 9.769 | 800 | length | Частично | Есть общая схема и начато подробное описание, но ответ обрывается на этапе  chunking . |

Во всех трёх прогонах finish_reason имел значение length. Это означает, что даже лимита 800 токенов оказалось недостаточно для полного подробного ответа на сформулированный запрос. Эксперимент наглядно показывает, что слишком маленький лимит приводит к потере содержания, а увеличение лимита повышает полноту, но одновременно увеличивает задержку: от 1,362 с при 100 токенах до 9,769 с при 800 токенах. Для полного подробного разбора такого запроса требуется лимит выше 800 токенов либо более жёсткое требование к лаконичности.

9. Рекомендуемая практическая конфигурация

В качестве прикладного сценария выбран первичный анализ события информационной безопасности. Для данного сценария важны фактическая корректность, отсутствие необоснованных выводов, устойчивый формат и умеренная длина ответа.

| Параметр | Рекомендуемое значение |
| --- | --- |
| Сценарий | Первичный анализ события информационной безопасности |
| Модель | google/gemma-3n-e4b |
| System prompt | Ассистент аналитика ИБ; не выдумывать данные; отделять факты от предположений; отвечать кратко и структурированно. |
| Temperature / sampling | 0.2 — низкая вариативность для более стабильного аналитического ответа |
| Ограничение   длины | max_tokens = 400 |
| Формат ответа | Факты / Гипотезы / Рекомендуемые действия |

Проверочный вызов выбранной конфигурации завершился за 2.652 с, использовал 205 токенов ответа и завершился с finish_reason = stop. Следовательно, лимит 400 токенов для данного сценария оказался достаточным. Модель корректно выделила факты, отдельно перечислила гипотезы и предложила практические действия. Такая конфигурация лучше подходит для первичной аналитической обработки, чем высокие значения temperature, поскольку здесь приоритетом является не разнообразие, а предсказуемость и структурированность результата.

10. Ошибки API и ограничения эксперимента

Во время 30 вызовов ошибок API не возникло; параметры temperature и max_tokens были приняты локальным OpenAI-совместимым API LM Studio. Параметр top_p в основной части не изменялся, поскольку методика рекомендует не менять одновременно несколько sampling-параметров, чтобы влияние каждого параметра можно было интерпретировать отдельно.

Наблюдаемым ограничением модели стало неполное выполнение инструкции «не выдумывай недостающие данные»: в sys_03 модель добавила субъективные уровни вероятности гипотез. Кроме того, при max_tokens = 800 объёмный ответ о RAG всё ещё был обрезан. Эти наблюдения подтверждают, что system prompt не является абсолютным механизмом контроля, а лимит генерации должен подбираться с учётом конкретной задачи.

11. Вывод

В лабораторной работе экспериментально исследовано влияние параметров генерации и системных инструкций на поведение модели google/gemma-3n-e4b.

Изменение system prompt заметно повлияло на структуру и объём ответа: ограничение до пяти пунктов сократило ответ и сделало его удобнее для практического анализа.

Формат «Факты / Гипотезы / Действия» модель соблюдала, однако полностью исключить необоснованные предположения одной системной инструкцией не удалось.

При temperature = 0 ответы были максимально стабильными, а набор предлагаемых названий практически не изменялся между повторами.

Повышение temperature до 0.3–0.7 увеличило разнообразие, причём в данной серии максимальное число различных названий было получено при 0.7.

Temperature = 1.0 также обеспечивала вариативность, но ответы становились менее равномерными по длине и структуре.

Эксперимент с max_tokens показал прямой компромисс между полнотой и затратами: при 100 и 300 токенах ответ явно обрывался, а даже 800 токенов оказалось недостаточно для полного подробного разбора семи этапов RAG.

Для первичного анализа события ИБ выбрана конфигурация с temperature = 0.2, max_tokens = 400 и жёстко заданным форматом ответа.

Проверочный вызов подтвердил, что такая конфигурация даёт краткий, структурированный ответ без обрыва и подходит для дальнейшего использования в прикладном прототипе.

Таким образом, параметры генерации следует выбирать не универсально, а по результатам измеримого эксперимента под требования конкретной информационной системы.

12. Ответы на контрольные вопросы

1. Что определяет system prompt и почему его нельзя считать механизмом защиты?

System prompt задаёт роль модели, постоянные правила, ограничения, стиль и ожидаемый формат ответа. Его нельзя считать механизмом защиты, потому что модель может выполнить инструкцию неполностью, а сама инструкция не заменяет проверку прав доступа, фильтрацию данных, валидацию действий и другие программные меры безопасности.

2. Как temperature влияет на выбор следующего токена?

Temperature изменяет распределение вероятностей при выборе следующего токена. Низкие значения делают выбор более сосредоточенным на наиболее вероятных токенах и повышают повторяемость; более высокие значения увеличивают вероятность менее очевидных вариантов и тем самым повышают разнообразие.

3. Почему высокий temperature не означает более высокое качество?

Высокая temperature увеличивает случайность, а не знания или способность модели рассуждать. Ответ может стать оригинальнее, но одновременно менее стабильным, менее точным или хуже соблюдать заданный формат.

4. Чем top_p концептуально отличается от temperature?

Temperature изменяет относительное распределение вероятностей токенов, а top_p ограничивает набор кандидатов токенами, суммарная вероятность которых достигает заданного порога p. Оба параметра управляют вариативностью, но делают это разными способами.

5. Почему не рекомендуется одновременно менять несколько sampling-параметров при учебном эксперименте?

Если одновременно изменить temperature и top_p, становится трудно определить, какой именно параметр вызвал наблюдаемое изменение. Для интерпретируемого эксперимента лучше менять одну настройку при фиксированных остальных.

6. Что произойдёт, если установить слишком маленький лимит длины ответа?

Генерация завершится до того, как модель закончит мысль или выполнит все пункты задания. В эксперименте это проявилось как finish_reason = length при лимитах 100, 300 и 800 токенов для объёмного RAG-запроса.

7. Почему повторяемость ответа важна для классификации и извлечения данных?

В таких задачах ожидается одинаковый результат при одинаковом входе. Высокая вариативность усложняет автоматическую обработку, тестирование и проверку результата, поэтому предпочтительны более стабильные настройки.

8. Почему значения параметров нельзя без проверки переносить с одной модели на другую?

Модели имеют разные архитектуры, обучение, настройки по умолчанию и поддержку параметров. Одинаковое численное значение temperature или лимита может приводить к разному поведению, поэтому конфигурацию необходимо проверять на конкретной модели.

9. Что делать, если выбранная модель не поддерживает temperature?

Следует зафиксировать сообщение API и ограничение модели в результатах, убрать неподдерживаемый параметр и продолжить эксперимент с доступными настройками. Сам факт ограничения является результатом лабораторной работы.

10. Какие параметры выбрать для генерации креативных идей и какие — для извлечения фактов?

Для креативных идей целесообразно использовать среднюю или повышенную temperature, например 0.7, поскольку она увеличивает разнообразие. Для извлечения фактов предпочтительна низкая temperature или минимально допустимое значение, жёсткий system prompt, структурированный формат и достаточный, но ограниченный max_tokens для повышения воспроизводимости.
